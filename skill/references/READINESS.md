# Readiness and result passport

Before implementation record functional and user outcomes, applicable visual/audio/performance/device criteria, planned checks and target environment. Keep small nonvisual tasks lightweight: their existing observable acceptance contract is sufficient; no visual stages or extra JSON are required.

For structured work use `add --readiness contract.json`. The object has nonempty `functional` and `user` string arrays, `target`, `checks` array, optional `launch` object, and `visual`, `audio`, `performance`, `device` objects. Each category has `relevant: true` plus `criteria`, or `relevant: false` plus a concrete `reason`. Do not weaken agreed criteria to get a pass. Launch is separate from planned tests: use `launch: {"status":"available","instructions":["npm run start"]}` or `{"status":"unavailable","reason":"Launch procedure not recorded"}`. Missing launch instructions remain explicitly unavailable; test commands never masquerade as launch steps.

Visual work must produce one early finished slice before scaling: keyframe, actual reference comparison, UI main flow and relevant audio. `visual-approve --target prototype` includes `finished_slice` with `keyframe`, `reference_comparison`, UI `main_flow`, relevant `audio`. Each is an object with `result: pass`, `tool`, `source`, `observation`. Unavailable observations use `result: not_verified`, `reason` and block production. Inspect real renders against inspected references, actual flows/performance and target devices when available. Never invent listening or physical-device testing.

New tasks default to `--approval-mode observed`. The historical `visual-approve` command accepts separate observed evidence: `origin: observed`, `observer_origin: independent-reviewer`, `decision: accepted`, `reviewer`, `tool`, `source`, `observation`, plus current `revision` and direction/palette or prototype digest. Reviewer must be separate from director and every author. This never represents user approval. Only when explicitly requested, use `--approval-mode explicit-user`: the existing sourced user decision/quote contract applies. Legacy tasks without a mode retain their prior explicit-user behavior. No mandatory user approval at every stage of already authorized work.

`review --readiness-evidence evidence.json` binds observations to `reviewer`, `snapshot` fingerprint, `contract_revision`, `attempt`, and `checks`. Checks contain exactly `functional`, `user`, `visual`, `audio`, `performance`, `device`; unknown keys are rejected so extra failed checks cannot hide behind passing categories. Applicable checks need `result: pass`, `tool`, `source`, `observation`; irrelevant checks need `result: not_applicable`, `reason`. Inconclusive/failing reviews can preserve `result: not_verified` or `fail` with reason. Relevant unavailable audio/device/performance cannot support PASS. Director integration checks and worker reports never replace independent reviewer observations. Unrun checks cannot support a passing general review. All records remain manual declarations, not proof of tool execution or identity.

`review --defects defects.json` records a nonempty JSON list: stable `id`, `criterion`, `priority` (`P0`-`P3`), `reproduction`, `cause`, `owner`, `status` (`open`, `fixed`, `not_verified`). Reuse one ID for the same defect. A second open failure of the SAME criterion blocks work, even if IDs differ. Continue only with `replan --diagnosis ... --changed-approach ... --reason ...`, explaining implementation, requirement or environment cause and the changed approach. Preserve criteria; bounded cycles require concrete escalation/follow-up, never endless retries or silent stopping.

`passport TASK` emits contract, artifacts, independent evidence, NOT VERIFIED items, limitations, separate launch instructions and planned checks. Evidence freshness binds the live repository snapshot, contract revision, attempt, author history and current independent review/state. Stale evidence is preserved under `historical_evidence` and explicitly marked NOT VERIFIED; it is never presented as current passing readiness. Current valid review reports remain available. Missing timing observations return null, including a missing latest submission; reversed or nonfinite observations are not fabricated as zero. JSON stats adds privacy-filtered delivery timing: creation through first submission is first-version wall time; first through latest submission is rework wall time, including waits. Missing observations remain null. Model usage in the passport stays null because the ledger has no authenticated usage source. Available observed event telemetry remains separate. Elapsed time never estimates tokens, money or savings.
